# ADR 0001: explicit synthetic resolver over private loopback mTLS

Status: accepted for the MVP; not a commitment to SDK-only long-term architecture.

Product-level architecture baseline: [Architecture ADR 0001](https://github.com/kredoxi/architecture/blob/main/docs/adr/0001-explicit-local-resolution.md), accepted on `architecture/main`.

## Decision
Use Go and its standard library, explicit resolution, loopback TLS 1.3 mutual
authentication, exact-reference policy and a generated in-memory provider.
No nonstandard cryptographic protocol, cloud dependency or privileged hook.
Go offers memory safety, portable HTTP/TLS and executable tests. Ordinary Go
memory remains observable to an authorized compromised process; no reliable
zeroization or dump prevention is claimed.

## Alternatives and feasibility

| Mechanism | Transparency / actual read interception | Identity and bypass | Privilege/platform/complexity |
|---|---|---|---|
| Explicit client + broker | Requires application call; portable, directly testable | mTLS key possession; authorized caller can exfiltrate | Unprivileged Go; small |
| OS local IPC | Explicit unless loader integrated | Peer credentials possible, executable attestation separate | Unix sockets/Windows named pipes; platform testing needed |
| Config-loader plugin | Intercepts only supported loader's reads | Same app compromise; plugin bypass | Application-specific; moderate |
| Process-launch wrapper | Can materialize env/config, not arbitrary later reads | Environment/disk residence undermines goal | Portable basics; lifecycle and child inheritance risk |
| Dynamic-loader/native hooks | Only hookable library paths; not static/direct syscalls | Hooks bypassable; no general identity guarantee | Linux loader/Windows DLL integration; invasive and risky |
| Windows services/interception | A service alone does not intercept config reads | Service/IPC ACLs help; privileged attacker wins | Windows-specific; privileges/compatibility verification |
| Filesystem/virtual filesystem | Can intercept supported mounts, not all reads | Mount bypass; process identity needs OS support | FUSE/drivers and installation; high complexity |
| Credential-aware proxy | Usually no application plaintext credential required | Must bind client/backend identity; protocol-specific | Moderate, per-target proxy; not universal config substitution |
| Container/Kubernetes integration | Mounted references still require integration | Workload identity possible, node/admin compromise | Extra deployment complexity; not justified locally |

Every plaintext-returning option still releases a credential into consumer
memory. Interception adds compatibility, bypass and privilege risks; a running
agent cannot magically replace a placeholder in an arbitrary file read.
SDK/broker latency is measurable using ordinary tests but no performance SLA
is established. Unknown OS/driver enforcement must be investigated in a
disposable environment, never inferred from user-mode telemetry.

## Consequences
The demo can prove reference-only configuration, private authenticated transport,
independent policy decisions, synthetic credential use and bounded safe failures.
One executable hosts the demo roles; independent process enrollment is future
work. No production CA, revocation, vault, protected telemetry or tamper monitor.
Next investigate OS-peer-authenticated IPC and enrollment with independently
tested consumer processes, preserving this explicit reference API as a baseline.
